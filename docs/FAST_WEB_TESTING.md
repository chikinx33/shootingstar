.\tools\run.ps1 deploy-web -Version 10.0.43+59

## 직전 지연의 원인

직전 V10 로그의 생성/수정 시각과 명령 결과를 확인했다. 실제 배포보다 배포 전 검수와 재시도가 오래 걸렸다. 아래 시간은 서로 겹치는 명령도 있으므로 단순 합산하지 않는다.

| 구간 | 확인한 시간 | 앞으로의 처리 |
|---|---:|---|
| 멈춘 `flutter analyze` 2회 | 합계 약 170초 | 기본 경로에서 제외. 필요 시 `dart analyze lib` 1회, 45초 제한 |
| Flutter 전체 테스트 명령 | 약 85초, 실제 테스트 실행 약 38초 | 변경한 기능의 관련 테스트만 선택 |
| 정식 웹 빌드 | 약 40초 | 변경 시 한 번만. 입력/출력/SDK가 같으면 재사용 |
| 별도 QA 진입점 빌드 | 약 34초 | 일반 배포에서 제외 |
| 광범위 브라우저 검사 구간 | 약 8분 28초 | 로비/출격 1회로 축소. 초기화 실패 후 전체 재실행 포함된 과거 구간 |
| Cloudflare 배포 명령 | 약 25초 | 유지. 업로드 자체가 주 지연 원인은 아니었음 |

근거는 `.local/v10-release-*.log`와 `tools/qa/evidence/v10-release/checks/`다. 이 시간은 과거 실측이며 다음 실행 속도를 보장하는 값은 아니다.

## 기본 명령

```powershell
# 로컬에서 확인할 빌드 + 작은 화면 실제 실행 1회
python tools/quick_web.py

# 다음 버전으로 빠른 웹 배포
python tools/quick_web.py --version 10.0.2+18 --deploy

# 같은 명령의 PowerShell 진입점
.\tools\run.ps1 quick-web
.\tools\run.ps1 deploy-web -Version 10.0.2+18

# 컴파일만 필요할 때: 내용이 같으면 기존 빌드 재사용
.\tools\run.ps1 build-web

# 바뀐 Dart 코드의 분석과 관련 테스트만 추가
python tools/quick_web.py --analyze --test test/ui_contract_test.dart --deploy
```

패치마다 버전명과 내부 빌드 번호를 모두 올린다. 이미 빌드한 같은 버전을 재확인/재배포할 때는 `--version`을 생략한다. `--build-only`는 로컬 컴파일용이고 `--deploy`와 함께 쓸 수 없다.

기본 순서는 **버전 동기화 → 소스 계약 → 변경 시 정식 웹 빌드 → 320px 로비 버전/가이드/출격/정지 확인 1회 → 선택한 경우 업로드 → 활성 배포 100%/API 확인**이다. npm predeploy가 최신 빌드·버전 검사를 한 번 수행하므로 직전에 같은 검사를 따로 반복하지 않는다. 로컬 단독 실행은 업로드 대신 빌드 검사를 수행한다.

`lib`, `web`, `assets`, pubspec/lock, 패키지 구성, SDK 메타데이터와 실제 빌드 출력의 내용 해시를 비교한다. 문서나 서버 코드만 바뀌면 클라이언트 컴파일은 재사용할 수 있다. 그림 교체, 버전 변경, 다른 진입점으로 빌드 덮어쓰기, 출력 파일 누락, SDK 변경은 재사용을 차단한다. `tools/qa/test_web_build_state.py`가 이 중 핵심 네 경우를 임시 파일로 확인한다.

## 검사를 확대할 때

| 변경 범위 | 추가할 검사 |
|---|---|
| 문서·배포 도구·버전 문자열 | 빠른 기본 경로만. 도구 변경은 해당 도구의 짧은 검사 |
| 한 화면의 UI/그림 | 그 화면 관련 위젯 테스트/실제 화면만 |
| 공통 레이아웃·글자·스크롤·내비게이션 | 기본320px1조건. 확산 위험/실패가 있을 때 해당 화면만 다른 폭·글자 확대 추가 |
| 전투·보상·저장·경제 규칙 | 관련 엔진/모델 테스트. 여러 시스템에 걸치면 전체 테스트 |
| 대규모 통합 변경·정식 출시 전 | 전체 회귀 검증. 일반 테스트 패치와 분리 |

통과 뒤 새 변경이나 실패 원인이 없으면 다시 검사하지 않는다. 버전 표시 한 줄을 바꿨다고 보급·길드·우편·수집품을 전부 다시 돌리지 않는다. 일반 배포에서 미실행한 전체 회귀를 "모두 통과"로 보고하지 않는다.

## 제한 시간과 증거

분석 45초, 관련 Flutter 테스트 120초, 빌드 180초, 짧은 웹 실행 45초, 배포 120초, 배포 조회 30초로 제한한다. 시간 초과 시 해당 명령의 자식 프로세스만 중단하고 실패를 기록한다. 무응답 분석기를 반복 실행하지 않는다. 실패하면 수정한 원인과 필요한 검사만 다시 실행한다.

공개 파일이 Access 로그인으로 이동하면 한 번 기록하고 멈춘다. 공개 화면/해시를 확인한 것으로 보고하지 않는다. 보안 설정은 변경하지 않는다. 활성 Worker와 API health는 별도로 확인한다.

같은 작업에서 이미 차단을 확인한 뒤 후속 패치를 배포할 때는 `--access-blocked-report .local/quick-web/<이미 확인한 실행>/report.json`을 추가한다. 도구는 제공된 보고서가 Access 차단을 기록하는지 확인하고 그 근거 경로를 새 보고서에 남기며 정적 파일을 다시 요청하지 않는다. 활성 Worker100%와 현재 버전의 API/D1 검사는 그대로 수행한다. 이 옵션은 공개 UI 검증을 통과했다는 뜻이 아니다.

업로드가 성공했는데 배포 후 확인만 실패했으면 **빌드·검수·업로드를 반복하지 않는다.** 보고서의 Worker ID로 `python tools/quick_web.py --verify-only <Worker-ID>`를 실행해 남은 확인만 재개한다. 실제로 새 배포 직후 기본 health URL이 이전 버전을 반환한 경우가 있어 확인 URL에 고유 쿼리를 붙였다. 버전 전파가 늦을 때만 최대 2초의 짧은 대기를 허용한다.

실행 단계별 시간/로그는 `.local/quick-web/<실행 시각>/report.json`, 마지막 실행은 `.local/quick-web/last-run.json`에 저장한다. 짧은 웹 화면과 결과는 `tools/qa/evidence/quick-web/<버전-빌드>/`에 두 장과 `smoke.json`으로 남긴다. 서버 계정·사용자 브라우저 저장소에는 쓰지 않는다. Android APK는 빌드하지 않는다.
